# Review follow-up — 8 September 2026

The 14 numbered findings below have been addressed. The original review is retained as a
historical snapshot; its line references, file names, sizes, and test counts describe the
pre-fix application, including files that have since been removed.

- Staged replacement and collision-safe publishing preserve existing audio. Windows device
  names and long filenames are handled, and metadata-disabled downloads retain their format.
- SQLite now owns live download state and commits each completed track before UI callbacks.
  Missing files are downloaded again; legacy CSV files are imported once and left untouched.
- Automatic matching rejects unsafe results, `--pick` uses the displayed result, and retry
  restores saved destinations and free-text options. Failures and batch diagnostics are saved;
  incomplete legacy records receive an explanation instead of disappearing from the summary.
- Configuration types, finite numeric values, TOML escaping, atomic saves, connection cleanup,
  progress feedback, and independent doctor checks are covered by regression tests.
- aria2 uses native scoped cookies, refreshes its worker when cookies change, cancels abandoned
  transfers, and shuts down cleanly. A real local-server test checks redirects, cookie expiry,
  path/domain/secure restrictions, cookie refresh, and closed worker ports.
- Removed the duplicate CLI, unused wrappers/types/settings/state writes, duplicate dependency
  manifests, and unreferenced image. The required runtime libraries and protocol regression
  behavior remain. Existing music, input exports, and legacy database history were preserved.

Verification: **112 tests passed, 1 skipped**; Ruff lint/format checks and Pyright passed across
both packages. The rebuilt source archive is **88,449 bytes** (previously 695,205,949), and the
wheel is **49,750 bytes**. Archive inspection found no music or personal CSV files. A clean
offline wheel installation passed version and command-help checks outside the checkout.

Limits: the FFmpeg integration test is skipped because FFmpeg is unavailable in this
environment; tagging failure and timeout paths are tested with controlled substitutes. Live
provider conversion/download was not tested. Transfers still buffer complete audio in memory,
and there is no overall track deadline; the README now states these timing limits accurately.
The repository remains uncommitted. See [CHANGELOG.md](F:/frogify-cli/CHANGELOG.md) for the
change list and [README.md](F:/frogify-cli/README.md) for current behavior.

## Original review — 6 September 2026

Frogify has a useful download engine and a reasonable dependency set, but the 2.0 migration is incomplete. The main problems are file safety, competing CSV and SQLite state, and gaps between the new CLI and the older implementation. Keep the protocol engine and simplify the code around it. I would fix the file-loss and release-package issues before distributing this version.

This review was completed on 6 September 2026. It covers all 26 application Python files, approximately 5,085 lines, the tests, configuration, documentation, dependencies, and existing release archives. No application code was changed and no music files were deleted. Offline reproductions used fake providers and isolated temporary files.

**Verification and its limits**

- The existing test suite completed with **72 passed and 1 skipped**. The skipped test exercises FFmpeg tagging; FFmpeg was unavailable in the review environment.
- The configured Ruff lint and formatting checks passed. Pyright reported **0 errors and 0 warnings**.
- These checks have limited scope: Ruff excludes `mp3juice` and `tests`, and Pyright includes only `frogify`. An explicit Ruff pass over the excluded directories found 32 findings, including six unused imports/variables. These are mostly cleanup issues, not the main defects below. See [check configuration](F:/frogify-cli/pyproject.toml:34).
- The new CLI tests replace the entire service with `FakeService`. No existing test directly exercises `FrogifyService`. Consequently, passing tests do not verify the new orchestration, SQLite resume, retry reconstruction, or real interactive selection. See [CLI tests](F:/frogify-cli/tests/integration/test_frogify_cli.py:16).
- Offline probes reproduced the file-loss, selection, persistence, validation, retry-destination, cookie-forwarding, and connection-cleanup problems described below.
- Live MP3Juice/Theta availability, actual download throughput, a fresh isolated installation, and an installed-binary aria2 transfer were not verified. Existing archive contents were inspected without extraction or execution.

**Problems, ordered by importance**

1. **[P1] A failed forced replacement deletes the original audio.** In a forced batch run, `final_path` can point to a previously successful file. If tagging fails, the exception handler unconditionally deletes that path. The tagging function already stages its new output separately, so this removes the old good file unnecessarily. The offline reproduction returned one failure and confirmed that the original file no longer existed. The old success CSV entry also remains, so later migration/resume can continue treating the deleted file as successful. Only clean up newly created temporary files; replace the existing file after the replacement is complete. [Replacement selection](F:/frogify-cli/mp3juice/spotify_batch.py:1105), [destructive cleanup](F:/frogify-cli/mp3juice/spotify_batch.py:1127).

2. **[P1 before distribution] The existing source release archive includes the local music library.** `dist/frogify-2.0.0.tar.gz` is **695,205,949 bytes**, roughly 695 MB. It contains 217 entries under `spotify`, totaling 701,008,474 uncompressed bytes, plus the Spotify export under `data`. The wheel is only 56,495 bytes and has the correct `frogify` console entry point. The current ignore file excludes `spotify` and `data`, but those exclusions do not repair the already-built archive. Delete or replace this generated archive, use an explicit source-package inclusion list, and inspect a rebuilt archive before publishing. This finding concerns the existing artifact; a fresh build was not performed. [Source archive](F:/frogify-cli/dist/frogify-2.0.0.tar.gz), [build configuration](F:/frogify-cli/pyproject.toml:28).

3. **[P2] SQLite is not actually the sole source of resume state.** The service asks SQLite whether to skip, calls the CSV-backed runner, then reads CSV files back to determine what happened. Legacy imports are marked complete by pathname, so later CSV changes are not imported. If a run writes its success CSV and stops before the SQLite update, the next runner can report `skipped`; the service handles every non-downloaded outcome as failure. I reproduced a valid existing audio file being recorded as a failed track. Have the runner return the actual outcome and path, persist that in SQLite, and derive compatibility reports from SQLite. Preserve one-time legacy import. [Service/runner handoff](F:/frogify-cli/frogify/core/service.py:218), [CSV skip](F:/frogify-cli/mp3juice/spotify_batch.py:992), [import marker](F:/frogify-cli/frogify/storage.py:218).

4. **[P2] Resume skips files that no longer exist.** `Database.is_success` checks only status. `_run_tracks` skips before checking the recorded file. A deleted or moved download therefore remains skipped until the user forces a reprocess. The reproduction produced `skipped=1, downloaded=0` for a missing file. Decide explicitly how output-directory changes should affect resume, and at least verify that the recorded audio is still a file. [Success lookup](F:/frogify-cli/frogify/storage.py:83), [skip decision](F:/frogify-cli/frogify/core/service.py:219).

5. **[P2] Automatic free-text matching can save an unrelated recording.** Free-text ranking supplies scores but never rejects candidates. The download service simply takes the first few results, even if every score is poor. A deliberately unrelated result scoring **37.79/100** was saved successfully in the reproduction. The free-text matcher also penalizes unexpected version words but does not enforce requested versions, unlike structured matching. Add a conservative automatic-acceptance rule and reject clearly incompatible versions; let an explicit selection override that rule when appropriate. Preserve the existing structured title/artist/duration gates. [Free-text ranking](F:/frogify-cli/frogify/matching.py:15), [automatic candidate selection](F:/frogify-cli/frogify/core/service.py:105).

6. **[P2] `--pick` can download a different result from the one selected.** The CLI searches and displays a list, collects a numeric index, and then `service.download` performs another search. Provider ordering or available results can change between calls. The reproduction displayed candidate `picked` and downloaded candidate `different`, with exit code 0. Pass the selected result itself to the download operation, or reuse the original ranked list. [Prompt and index](F:/frogify-cli/frogify/cli/app.py:126), [second search](F:/frogify-cli/frogify/core/service.py:105).

7. **[P2] Expected failures are not consistently translated or persisted.** The CLI catches `FrogifyError`, but the provider adapter forwards the separate `mp3juice.exceptions.SearchError`. A search outage escaped the friendly error handler and created no persisted failure. An empty result list also exits before failure recording. Missing FFmpeg raises an uncaught `RuntimeError`, and the batch runner checks FFmpeg during construction even when every track should be skipped. Normalize expected provider/dependency failures at the service boundary, persist actionable download failures, and defer FFmpeg checks until tagging is needed. [Adapter](F:/frogify-cli/frogify/providers/mp3juice.py:15), [CLI catch](F:/frogify-cli/frogify/cli/app.py:141), [failure persistence](F:/frogify-cli/frogify/core/service.py:143), [FFmpeg check](F:/frogify-cli/mp3juice/spotify_batch.py:958).

8. **[P2] Retry does not reconstruct the original operation completely.** Structured failure payloads store `output_dir`, but retry discards it and uses the current configuration or working directory. The offline check confirmed that the stored destination never reaches `_run_tracks`. Free-text failures store only the query, losing source selection and output preferences. Structured failures with missing/zero duration are silently omitted from the retry summary even though the database marks them retryable. Restore saved execution options unless explicitly overridden, and explain failures that cannot be reconstructed. [Retry](F:/frogify-cli/frogify/core/service.py:264), [saved destination](F:/frogify-cli/frogify/core/service.py:297).

9. **[P2] Configuration and CSV validation accept values that break later operations.** A negative network timeout, a `nan` duration tolerance, and a CSV duration of `nan` were accepted. Nonfinite values undermine duration comparisons. Manually supplied TOML booleans/types are not comprehensively checked either. The TOML writer escapes quotes and backslashes but not newlines: setting a string containing a newline successfully wrote a configuration that the next load rejected. Validate types, ranges, and finite numbers before use, correctly escape strings, and write configuration atomically. [Configuration validation/writer](F:/frogify-cli/frogify/config.py:108), [CSV duration parsing](F:/frogify-cli/mp3juice/spotify_batch.py:119).

10. **[P2] Disabling metadata can save non-MP3 bytes under an `.mp3` filename.** Every canonical batch path ends in `.mp3`. With metadata disabled, the runner moves the raw file there without conversion, even when `song.ext` is `ogg`, `m4a`, or another supported format. The reproduction saved an Ogg payload as `Song.mp3`. Preserve the source extension when copying raw audio, or separate format conversion from the metadata setting. [Filename construction](F:/frogify-cli/mp3juice/spotify_batch.py:657), [metadata-off branch](F:/frogify-cli/mp3juice/spotify_batch.py:1117).

11. **[P2] Filename collision and Windows handling are incomplete.** The final URI-suffixed fallback is returned without checking whether it already exists; subsequent replacement can overwrite it even without `--force`. I reproduced the helper returning an occupied path. The sanitizer also leaves Windows device names such as `CON` and `NUL` unchanged. Separately capped title and artist strings can combine into a 367-character filename. Check every fallback, handle reserved names, and cap the complete filename. [Collision fallback](F:/frogify-cli/mp3juice/spotify_batch.py:657), [sanitizer](F:/frogify-cli/mp3juice/utils.py:28).

12. **[P2] aria2 receives cookies without their original domain/path restrictions.** `_final_download_headers` flattens the entire session cookie jar into one `Cookie` header, then sends it to the final download endpoint. An invented cookie restricted to `mp3juice.sc/account` appeared in that header even though the final endpoint is independently supplied by the resolver. This is a concrete scoping problem; no real credential leak was observed. Build cookies for the actual destination URL or use a cookie mechanism that preserves domain/path scope. [Cookie flattening](F:/frogify-cli/mp3juice/client.py:733), [aria2 handoff](F:/frogify-cli/mp3juice/client.py:827).

13. **[P2] SQLite connections are not explicitly closed.** `with self.connect()` manages transaction commit/rollback but does not close the connection. Each lookup and write opens another connection and relies on garbage collection for cleanup. Python emitted an `unclosed database` ResourceWarning in the reproduction. Use a clearly owned connection for the operation or close each connection in a context manager/finally block. Keep transaction handling. [Connection creation](F:/frogify-cli/frogify/storage.py:29).

14. **[P2, usability] The new CLI drops the existing progress feedback.** The download service and batch runner already support progress/status callbacks, but the new CLI passes none. A large batch produces its first useful summary only when it finishes, while a single download remains labeled as searching throughout transfer. Wire a small amount of Rich progress/status rendering into the existing callbacks. Since the service calls `runner.run([track])` repeatedly, fix the always-1-of-1 batch callback numbering at the same time. [Single download call](F:/frogify-cli/frogify/cli/app.py:132), [batch call](F:/frogify-cli/frogify/cli/app.py:169), [per-track runner invocation](F:/frogify-cli/frogify/core/service.py:222).

**Other worthwhile corrections**

- `doctor` constructs and initializes the service/database before its diagnostic checks run. A database initialization failure can prevent the very diagnostic meant to describe it. An invalid config can also fail again in the unguarded output-directory lookup after being caught once. Make diagnostics independently usable. Its HTTP checks report 404 as OK; that proves an HTTP server responded, not that the provider operation works. Label that distinction clearly. `--deep` currently only adds a placeholder result. [Doctor](F:/frogify-cli/frogify/diagnostics.py:31), [service initialization](F:/frogify-cli/frogify/core/service.py:47).
- There is no overall per-track deadline. HTTP retries are count-bounded, but batch processing tries every accepted candidate; aria2 polls until a terminal state, and FFmpeg/ffprobe subprocesses have no timeout. The README's assurance that no profile spends minutes on a track is stronger than the implementation guarantees. Bound the complete operation or narrow the documentation. No actual indefinite hang was observed. [Candidate loop](F:/frogify-cli/mp3juice/spotify_batch.py:1029), [aria2 loop](F:/frogify-cli/mp3juice/aria2_downloader.py:209), [subprocess](F:/frogify-cli/mp3juice/spotify_batch.py:648).
- Repeated CSV load/rewrite/readback creates avoidable work as a library grows. A single-track runner invocation rewrites whole reports, including final persistence, and `_csv_row` scans them again. Remove this through the SQLite consolidation above. The complexity is visible in the code; a large-library performance benchmark was not run. [Runner persistence](F:/frogify-cli/mp3juice/spotify_batch.py:1187), [CSV readback](F:/frogify-cli/frogify/core/service.py:332).
- Requests collects the whole file in a chunk list and joins it; aria2 reads its completed temporary file back into memory, and batch then writes the bytes out again. That is acceptable for short tracks, but memory use grows with recording size. Reuse a temporary-file path if long recordings are an intended use case; an async rewrite is unnecessary. [Requests buffering](F:/frogify-cli/mp3juice/client.py:766), [aria2 readback](F:/frogify-cli/mp3juice/aria2_downloader.py:261).
- Invalid CSV identities use only the row number, so row 2 in two different imports shares an identity. Include a source identifier if retaining invalid-row history matters. [Invalid-row identity](F:/frogify-cli/frogify/core/service.py:248).
- Git has no commits and application files are untracked. Establish a reviewed baseline before cleanup so deletion and behavioral changes are easy to compare and undo. The ignore file changed during this review; the latest exclusions were respected.

**What is right and should stay**

- Search is separate from conversion and transfer. Listing results does not convert every candidate or consume all the short-lived download URLs. [Search](F:/frogify-cli/mp3juice/client.py:477).
- Structured matching has substantive safeguards: title, artist, duration, requested/unrequested recording versions, and post-download duration validation. The tests protect real edge cases such as neutral upload labels and omitted Original Mix/Album Mix labels. [Matching](F:/frogify-cli/mp3juice/spotify_batch.py:367), [matching tests](F:/frogify-cli/tests/test_spotify_batch.py:51).
- The resolver supports both observed redirect and direct-download response shapes. Its bounded 429/transient retries, shared pacing, worker-error detection, and audio-payload checks solve distinct problems. Keep those behaviors and their tests; removing them would trade working reliability for fewer lines. [Resolution](F:/frogify-cli/mp3juice/client.py:592), [retry profiles](F:/frogify-cli/mp3juice/retry.py:23).
- SQLite, the standard TOML reader, dataclasses, and platformdirs are sensible choices. There is no ORM, web framework, custom plugin system, or unnecessary async framework to remove. The service/client injection points are useful for real offline tests once the service itself is exercised.
- FFmpeg tagging stages output and avoids re-encoding MP3 input. CSV exports are written via temporary files and atomic replacement. Keep those mechanisms and fix the caller's destructive cleanup. [Tagging](F:/frogify-cli/mp3juice/spotify_batch.py:592), [CSV writer](F:/frogify-cli/mp3juice/spotify_batch.py:517).
- aria2 is optional; automatic mode has a requests fallback. Its RPC worker listens locally, uses a random secret, and suppresses an unnecessary Windows console window. The optional transfer accelerator is not proven bloat. [aria2 startup](F:/frogify-cli/mp3juice/aria2_downloader.py:73).
- The six directly used runtime libraries have clear jobs: Requests for HTTP, Mutagen for audio inspection, RapidFuzz for matching, platformdirs for state locations, Typer for argument parsing, and Rich for rendering. There is no compelling dependency-removal target here.
- Log rotation and signed-query-parameter redaction are useful. Preserve them while making sure future diagnostics do not put raw auth material or sensitive URLs into CSV/SQLite records outside the formatter. [Logging](F:/frogify-cli/frogify/logging.py:10).

The practical order is to protect existing files and rebuild the release archive, then fix selection/error handling and make SQLite authoritative. Add a small set of real service integration tests for those paths, restore basic progress, and retire the duplicate CLI and unused wrappers. Expand checks to cover the protocol code before further refactoring. A rewrite or more infrastructure is unnecessary.
